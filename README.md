# DependencyVisualisation

## Общее описание

CLI-инструмент анализа зависимостей пакетов Rust (Cargo), вариант № 2.
На этапе 3 программа строит граф прямых и транзитивных зависимостей алгоритмом BFS
без рекурсии. Источник данных - HTTP(S)-индекс Cargo или локальный тестовый граф.

Реализованные функции:

- Чтение INI-файла и проверка всех пяти параметров конфигурации.
- Построение адреса записи индекса по имени пакета и HTTP-загрузка с тайм-аутом 5 секунд.
- Разбор JSONL: каждый объект описывает одну опубликованную версию пакета.
- Сравнение версий по SemVer 2.0.0, включая prerelease и метаданные сборки.
- Выбор максимальной по SemVer неотозванной версии без prerelease.
  При равном приоритете выбирается первый подходящий элемент индекса.
- Обход в ширину с ограничением глубины; глубина корневого пакета равна `0`.
- Сохранение циклических ребер, петель и общих зависимостей без повторного обхода пакета.
- Чтение тестового графа из JSON с проверкой имен и наличия указанных зависимостей.
- Вывод построенного графа списком смежности и обработка ошибок источника и выбора версии.

Данные получаются самостоятельно через `net/http` и разбираются средствами `encoding/json`.
Для чтения настроек используется `gopkg.in/ini.v1`.
Формат источника описан в [документации индекса Cargo](https://doc.rust-lang.org/cargo/reference/registry-index.html),
порядок версий — в [SemVer 2.0.0](https://semver.org/).

При чтении индекса учитываются все записи `deps` выбранной версии: обычные, сборочные,
тестовые, необязательные и платформенные зависимости. В метаданных одинаковые имена
могут повторяться, например при разных требованиях к версиям. Для переименованной
зависимости используется настоящее имя пакета из поля `package` индекса.

Для каждого имени выбирается один максимальный стабильный неотозванный релиз.
Требования `req` сохраняются в метаданных, но не ограничивают выбор версии при обходе.
Каждый пакет загружается один раз за построение графа. Повторные зависимости
между теми же вершинами дают одно ребро; порядок первого появления ребер сохраняется.
Вершины на предельной глубине входят в граф, их исходящие ребра не раскрываются.
ASCII-дерево и графическая визуализация относятся к этапу 5.

Основные функции кода:

| Пакет | Назначение |
| --- | --- |
| `config` | `MustLoadConfig` читает INI; внутренние функции проверяют структуру и значения. |
| `cargo` | `NewClient` создает клиент, `LoadVersions` загружает и разбирает все версии пакета. |
| `analyzer` | `New` принимает `PackageSource`, `PackageDependencies` возвращает выбранную версию с зависимостями. |
| `analyzer` | `BuildGraph` строит граф BFS до заданной глубины; `expandGraph` добавляет ребра и новые вершины. |
| `analyzer` | `CompareVersions` сравнивает два номера SemVer; внутренний `selectVersion` выбирает максимум. |
| `testrepo` | `Load` читает и проверяет JSON-граф, `LoadVersions` предоставляет пакет анализатору. |
| `domain` | `PackageVersion` и `Dependency` хранят метаданные, `PackageID` и `Graph` описывают граф. |
| `main` | Загружает настройки, выбирает источник и печатает список смежности через `printGraph`. |

Подробная документация функций, включая внутренние, доступна через Godoc.

## Настройки

Все пять параметров обязательны в секции `[visualizer]`:

```ini
[visualizer]
package_name = serde
repository = https://index.crates.io/
test_mode = false
ascii_tree = false
max_depth = 3
```

| Параметр | Описание |
| --- | --- |
| `package_name` | Имя Cargo-пакета, например `serde`; в тестовом режиме - только заглавные латинские буквы. |
| `repository` | Базовый HTTP(S)-URL индекса Cargo или путь к JSON-файлу тестового графа. |
| `test_mode` | При `true` используется локальный граф, при `false` - HTTP(S)-индекс. |
| `ascii_tree` | Булево значение; проверяется при чтении. Вывод ASCII-дерева относится к этапу 5. |
| `max_depth` | Максимальная глубина BFS, целое число от `0`. При `0` граф содержит только корень. |

Параметр `ascii_tree` на этапе 3 не меняет вывод.
Файл тестового репозитория содержит объект со списками смежности:

```json
{"A": ["B", "C"], "B": ["C"], "C": []}
```

Ключ - имя пакета, массив - имена его прямых зависимостей. Все имена должны
соответствовать `[A-Z]+`, включая многобуквенные имена. Каждая зависимость должна
быть объявлена ключом; пустой массив обозначает пакет без зависимостей.
Циклы и повторения разрешены. Тестовым пакетам назначается условная версия `1.0.0`.

Относительные пути задаются от рабочего каталога процесса.
Путь к INI передается флагом `-config`; по умолчанию используется `tests/example.ini`.
Ошибки чтения и проверки конфигурации завершают приложение через `panic` в `stderr`.
Ошибки анализа выводятся в `stderr`, код завершения приложения — `1`.
Успешный результат выводится в `stdout`, код завершения — `0`.

## Сборка и тесты

Требуются Go 1.26.4 или новее и Make. Команды выполняются из корня репозитория:

```sh
make build
make test
```

Собранное приложение находится в `bin/visualiser`; каталог `bin` исключен из Git.
Автоматические тесты расположены рядом с кодом в `config`, `cargo`, `analyzer` и `testrepo`.
HTTP-тесты используют локальные серверы. В `tests` находятся примеры INI и
синтетический ответ индекса `cargo_versions.jsonl` для проверки парсера,
а также тестовый граф `graph.json` с настройками `graph.ini`.
Проверки графа охватывают глубину, порядок BFS, циклы, петли, общие и повторные зависимости.

Дополнительные проверки и просмотр документации:

```sh
go vet -mod=readonly ./...
go mod verify
go doc -u -all ./src/internal/analyzer
go doc -u -all ./src/internal/cargo
```

## Примеры запуска

Запуск анализа Cargo-пакета из `tests/example.ini`:

```sh
make run
```

Для воспроизводимой демонстрации без сети:

```sh
make run CONFIG=tests/graph.ini
```

Результат для корня `A` и `max_depth = 3`:

```text
Пакет: A 1.0.0
Граф зависимостей:
  A 1.0.0: B 1.0.0, C 1.0.0
  B 1.0.0: D 1.0.0
  C 1.0.0: D 1.0.0, A 1.0.0
  D 1.0.0: D 1.0.0, E 1.0.0
  E 1.0.0: -
```

Строки пакетов отсортированы по имени и версии. `-` означает отсутствие
исходящих ребер в построенном графе, в том числе из-за ограничения глубины.
В обычном режиме версии и зависимости определяются текущим содержимым индекса.

Для других случаев измените `package_name` и `max_depth` в `tests/graph.ini`
и повторите ту же команду:

| Корень | Глубина | Результат |
| --- | ---: | --- |
| `Z` | `3` | Одиночный пакет без ребер. |
| `A` | `0` | Только корневой пакет. |
| `A` | `1` | Ветвление `A → B, C`; зависимости `B` и `C` не раскрыты. |
| `A` | `2` | Общая зависимость `D` и цикл `A → C → A`; исходящие ребра `D` не раскрыты. |
| `A` | `3` | Полный граф, включая петлю `D → D` и конечную вершину `E`. |
| `B` | `1` | Цепочка `B → D` с остановкой на границе глубины. |

Необъявленный корень, поврежденный JSON, неверные имена и ссылки на отсутствующие
пакеты завершают анализ с сообщением об ошибке.

Запуск собранного приложения с явно указанным INI:

```sh
./bin/visualiser -config tests/example.ini
```

Для анализа другого пакета измените `package_name` в INI-файле.
Другой файл конфигурации можно выбрать через Make:

```sh
make run CONFIG=путь/к/настройкам.ini
```

Выбор INI и демонстрация ошибки имени пакета:

```sh
make run CONFIG=tests/invalid_package.ini
```

Ожидается `panic` с сообщением `неверное значение package_name: "bad/name"`.
Другие примеры ошибок: `tests/invalid_repository.ini`, `tests/invalid_test_mode.ini`,
`tests/invalid_ascii_tree.ini`, `tests/invalid_max_depth.ini`.
